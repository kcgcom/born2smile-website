# 방문자·콘텐츠 반응 분석 재설계안

작성일: 2026-11-14. 아래는 초기 조사·설계 기록이다. 이후 1차 로컬 구현을 진행했으며 현재 상태와 검증은 [구현 기록](customer-analytics-implementation.md), 구체적인 계약은 [측정 명세](customer-analytics-measurement-contract.md)를 따른다. 운영에는 배포하지 않았다.
초기 설계 후 2026-11-14에 최근 30일 운영 이벤트 집계를 추가 점검했다. 결과는 [수집 상태 점검](customer-analytics-audit-2026-11-14.md)을 따른다. 아래 설계의 미확인 항목 중 이벤트 존재·누락 현황은 해당 점검으로 보완됐다. 프로젝트 설정·과금·배포 후 실제 동작 검증은 남아 있다.

## 1. 목적과 범위

서울본치과 사이트에서 다음 질문에 답할 수 있게 한다.

1. 어떤 경로가 관심 있는 방문자를 데려오는가?
2. 어떤 콘텐츠가 충분히 읽히고 반응을 얻는가?
3. 어떤 콘텐츠 이용 뒤 병원 정보 확인과 문의 시도가 이어지는가?
4. 어느 화면·기기에서 탐색이나 문의가 막히는가?

정보를 얻고 떠난 방문과 병원 문의로 이어진 방문을 모두 별도의 성과로 인정한다. 관련 글 이동·문의가 없다는 이유로 글의 유용성을 낮게 평가하지 않는다. 분석 단위는 익명 브라우저 방문이며 실제 환자 수와 같지 않다.

이번 문서는 조사·계획 산출물이다. 자동 추천 순위, 운영 배포, PostHog 설정 변경, 예약 시스템 연동은 구현하지 않는다. 분석을 위해 개인별 진료 관심 프로필이나 환자 식별자 연결을 만들지 않는다.

| [목록](../components/blog/BlogContent.tsx) | 목록 좋아요 이벤트 없음, 공유는 이벤트 있음 | 상세 반응과 목록 반응 분리, 좋아요 수집 범위 보완 |
| [공유 유입](../components/blog/BlogShareVisitTracker.tsx) | 공유 URL 파라미터와 sessionStorage로 유입 기록 | 고유 수신자·공유 완료·원본 공유와의 일대일 연결로 해석 금지 |
| [공유 표시](../app/admin/(dashboard)/components/analytics-display.ts) | 공유 1회당 유입을 이벤트 비율로 설명 | 해당 설명 유지; 성공률·전환율로 바꾸지 않음 |
| [본문 페이지](../app/blog/[category]/[slug]/page.tsx) | 본문 외 헤더·목차·저자 소개·관련 링크·CTA 존재 | 페이지 전체 스크롤과 본문 도달률을 분리 |
| [현재 읽기 시간 계산](../lib/blog-supabase.ts) | 블록 문자 수 기반, 관련 링크의 URL 등도 포함 | 표시용 분 문자열을 실제 읽기 기준으로 바로 사용하지 않음 |

설치 lockfile의 posthog-js는 1.364.5다. 로컬 SDK 소스맵에서 `$prev_pageview_duration`이 페이지뷰 시각 차이로 계산됨을 확인했다. 이전 페이지 스크롤 속성도 있으므로 기존 이벤트를 먼저 점검하되, 본문 활성 읽기 시간과 동일한 값으로 사용하지 않는다. 최신 공식 문서의 기능을 쓰기 전 설치 버전 지원 여부를 확인한다.

추가 조사 사항: 목록 좋아요는 RPC 결과의 `error`를 확인하지 않는 경로가 있다. 추후 수집 보완 시 성공한 반응만 보내도록 이 경로도 검증한다. 공유 발생 이벤트는 `source`, 공유 유입은 `share_source`를 사용하지만 현재 위치별 쿼리는 `share_source`만 읽으므로 위치별 비교 전에 속성 매핑을 검증한다. 이번에 수정하지는 않았다.

## 3. 측정할 항목과 운영 판단

| 영역 | 측정 | 운영에 사용할 질문 | 우선순위 |
|---|---|---|---|
| 유입 | 세션 유입 채널·UTM·첫 페이지·기기, 신규/재방문 브라우저 | 어떤 경로에서 읽기·문의가 발생하는가? | 1 |
| 읽기 | 글별 측정 가능 방문, 본문 도달 단계, 활성 읽기 시간 단계, 유효 읽기 | 조회가 많은 글과 실제 읽히는 글이 같은가? | 1 |
| 직접 반응 | 좋아요 추가/취소, 네이티브 공유 동작, 링크 복사 | 어떤 글에 독자가 반응하는가? | 1 |
| 병원 정보 확인 | 진료 소개·의료진·위치/진료시간 페이지 방문 | 콘텐츠 이용 뒤 어떤 정보를 더 확인하는가? | 1 |
| 문의 의도 | 전화·카카오·문의 안내 클릭, 발생 페이지·버튼 위치 | 어느 경로에서 문의를 시도하는가? | 1 |
| 수집 품질 | 누락 필드·중복·분모 없는 반응·API 오류·수집 시작일 | 숫자를 믿을 수 있는가? | 1 |
| 탐색 품질 | 목록 필터·검색 결과 수·결과 없음, 추천 노출/클릭 | 원하는 정보를 찾기 어려운가? | 2 |
| 재방문 | 첫 방문 코호트별 7일·30일 재방문 | 다시 찾는 콘텐츠가 있는가? | 2 |
| 실제 성과 | 실제 상담 접수·예약 확정·방문 | 문의 의도가 실제 성과로 이어졌는가? | 별도 연동 |

전화·카카오 클릭은 문의 의도다. 현 사이트는 전화 예약을 안내하며, 클릭만으로 통화 연결·상담 완료·예약 확정을 알 수 없다. 실제 성과는 예약/상담 시스템에서 신뢰할 수 있는 결과를 받을 때 별도 설계한다.

전체 방문자를 반드시 동일한 순서의 퍼널에 넣지 않는다. 정보 해결 경로, 병원 탐색 경로, 바로 전화하는 경로를 나누어 본다. 병원 소개 방문은 신뢰의 증거가 아니라 정보 확인 행동이다.

## 4. 핵심 지표 정의

### 공통 단위

- 방문 기준 기본 단위는 PostHog 세션 + 글 식별자다. 반복 새로고침·좋아요 클릭을 여러 독자로 세지 않는다.
- 개별 본문 진입마다 `article_view_id`를 생성해 읽기와 상세 반응을 연결한다. SPA에서 다른 글 진입 시 새 ID, StrictMode effect 재실행은 같은 ID, BFCache 복원은 같은 ID를 유지한다.
- 실제 읽기 조건은 같은 `article_view_id` 안에서 충족해야 한다. 서로 다른 방문의 시간과 스크롤을 합쳐 충족 처리하지 않는다. 결과를 세션+글 단위로 한 번 집계한다.
- 세션 ID가 없으면 view 단위 진단에만 포함하고, 세션 지표에 섞지 않는다. 미수집·차단 방문은 알 수 없으므로 전체 방문자라고 표시하지 않는다.
- 분모 0은 0%가 아닌 `—`; 미설정·실패·부분 응답·수집 전 기간은 별도 상태다.

### 첫 관리자 리포트

| 지표 | 분자 / 분모 |
|---|---|
| 유효 읽기율 | 유효 읽기가 발생한 세션+글 / 측정 가능 본문 방문 세션+글 |
| 본문 75% 도달률 | 해당 깊이에 도달한 세션+글 / 같은 본문 방문 세션+글 |
| 상세 좋아요 반응률 | 상세에서 like 행동이 한 번 이상 발생한 세션+글 / 같은 본문 방문 세션+글 |
| 상세 공유 행동률 | 상세에서 공유/복사 행동이 한 번 이상 발생한 세션+글 / 같은 본문 방문 세션+글 |
| 문의 시도율 | 문의 클릭이 발생한 세션 / 같은 분석 모집단의 세션 |
| 콘텐츠 이용 후 문의율 | 글 이용 이후 같은 세션에서 문의한 세션 / 해당 글을 이용한 세션 |

좋아요 반응률은 현재 좋아요를 유지하는 사용자 비율이 아니다. 취소 건수는 별도로 보여주고 Supabase 누적 좋아요와 혼합하지 않는다. 목록에서 반응한 사람은 본문 방문 분모에 넣지 않는다. 여러 글을 읽은 뒤 문의하면 여러 글에 연관될 수 있으므로 글별 문의 수를 합해 전체 문의 수로 사용하지 않는다. 인과 효과로 표현하지 않는다.

기간은 새 리포트 내에서 KST 기준 전일까지 완료된 7/30/90일로 통일하고 시작·종료 시각을 응답한다. 범위 안에 시작된 view와 그 범위 안에서 발생한 반응을 연결한다. 기간 경계를 넘긴 반응은 해당 기간 비율에서 제외된다는 점을 명시한다. 과거 GA4/기존 rolling 리포트는 각각 원래 기간을 표시하며 새 지표와 직접 나누지 않는다.

표본 수를 비율 옆에 항상 표시한다. 초기 `30세션 미만: 표본 부족` 표시는 운영용 제안값이며 통계적 유의성의 보장이 아니다. 자동 노출 점수·가중치·우열 판정은 이번 단계에 넣지 않는다. 글 길이·기기·유입 채널별로 비교하고, 관련 글 개수와 다음 글 이동은 개별 글 점수에서 제외한다.

## 5. 읽기 이벤트 설계안

새 이벤트는 PostHog 전용 전송 경로로 보낸다. 기존 CTA·공유의 GA4 전송은 유지한다. 공통 제외 정책은 재사용하고, 자동 수집·세션 녹화는 확대하지 않는다.

| 이벤트 | 발생 시점 | 횟수 제한 |
|---|---|---|
| `blog_article_viewed` | 공개 상세 페이지가 렌더되고 visible 상태에서 추적 준비 완료 | view당 1회 |
| `blog_read_progress` | 본문 깊이 25/50/75/90% 또는 활성 시간 15/30/60/90초 최초 도달 | 깊이 4 + 시간 4 이하 |
| `blog_read_qualified` | 같은 view에서 깊이와 글 길이별 시간 기준 모두 충족 | view당 1회 |

추가 자동 이벤트 예산은 본문 view당 최대 10개다. 매 스크롤·매 초 네트워크 전송은 하지 않는다. 기존 페이지뷰·CTA·직접 반응 이벤트는 이 예산과 별도다. 월간 추가 이벤트의 보수적 상한은 측정 가능 상세 view × 10이며 실제 비용은 프로젝트 전체 이벤트 사용량과 현재 계약을 확인해 판단한다.

공통 속성: `measurement_version`, `article_view_id`, `blog_slug`, `category`, `page_type=blog_post`, 정규화한 `page_path`, `content_revision`, `readable_char_count`, `estimated_read_seconds`, `required_active_seconds`.
진행 속성: `milestone_type`, `milestone_value`, `active_read_seconds`, `max_body_depth_pct`, `anchor_navigation_used`.
본문 원문·검색 자유입력·연락처·환자 정보는 추가 이벤트 속성으로 보내지 않는다. 기존 SDK가 자동 부착하는 URL·referrer 속성까지 실제 payload에서 확인한다.

첫 유효 읽기 기준 제안은 본문 75% 도달 + `clamp(15초, 예상 읽기 시간 × 25%, 90초)`다. 앞서 대화의 60%·30초는 예시였으며 확정 기준이 아니다. 이번 값도 초기 실험값이며 수집 후 조정한다. 기준을 바꾸면 버전을 올려 서로 다른 정의를 섞지 않는다.

예상 읽기 시간은 표시용 `readTime` 문자열 대신 노출되는 교육 본문 문자 수에서 계산한다. 기존 분당 500자를 초기 가정으로 사용할 수 있지만 실제 속도의 보장은 아니다. relatedLinks·URL·저자 소개·CTA를 제외하고 FAQ·표·노출 캡션을 포함한다. 교육용 이미지가 많은 글은 별도 구분해 비교한다.

### 브라우저 동작

- 측정 경계는 제목/목차/저자 소개가 아닌 교육 본문이다. 본문 안의 관련 링크 블록도 제외할 수 있도록 렌더러에 명시적인 측정 표식을 설계한다.
- 본문 도달률은 읽기 완료율이 아니다. 각 교육 블록 높이를 누적한 좌표에서 viewport가 도달한 최대 위치를 사용하고, 제외 블록 높이는 총 길이에 더하지 않는다. 목차 점프는 중간을 읽었다는 뜻이 아니므로 점프 여부를 기록해 분리 분석한다.
- `document.visibilityState`가 visible이고 본문이 viewport에 보일 때만 시간을 누적한다. 긴 비활동 방치는 초기 60초 idle 제한으로 중단하고 스크롤·포인터·키보드·터치 활동 시 재개한다. 정지 상태로 천천히 읽는 독자가 과소 측정될 수 있음을 명시한다.
- monotonic clock을 쓰고 숨김·잠금·긴 타이머 지연·복귀 사이의 시간을 그대로 더하지 않는다. 활성 구간을 잘라 합산한다.
- 이미지·폰트·FAQ 확장·화면 회전·리사이즈 후 레이아웃을 재측정한다. 단순 반응형 변경으로 새 view를 만들지 않는다.
- hidden/pagehide에서 로컬 시간을 정리하고 BFCache 복원 시 기준 시각을 재설정한다. 종료 이벤트 전송 성공에 의존하지 않고 임계점 도달 즉시 기록한다.
- 자동 이벤트를 모두 보낸 뒤에는 불필요한 관찰자·타이머를 정리한다. 앱 렌더 상태를 매 스크롤 갱신하지 않는다.
- 저장소 접근 실패·SDK 미설정·opt-out·관리자 방문 시 읽기 UI가 실패하지 않게 한다. 추적 실패를 보충하려고 다른 공급자에 우회 전송하지 않는다.

시간 단계만 수집하면 정확한 최종 읽기 시간을 알 수 없다. 따라서 초기 화면은 ‘30초 이상 비율’ 등 단계 비율을 사용하고 이를 평균 읽기 시간이라고 표시하지 않는다. 정밀한 시간 분포가 실제로 필요해질 때 종료 요약/체크포인트 설계를 별도로 검토한다.

## 6. 기존 반응·문의 이벤트 정리

- 기존 이벤트 이름을 즉시 폐기하지 않고 새 속성 계약을 정의한다. 과거 호환 쿼리와 수집 시작일을 둔다.
- 상세 좋아요·공유에 같은 `article_view_id`와 페이지 문맥을 부착한다. 목록에는 `surface=list_card`를 붙이며 상세 읽기율 계산에서 제외한다.
- 목록 좋아요는 RPC 성공을 확인한 후 like/unlike 이벤트를 보낸다. Supabase 사용자 식별자를 PostHog 개인 식별자로 복사하지 않는다.
- `source`/`share_source`를 구분해 기존 위치별 집계를 수정하고, 공유 버튼 위치·공유 유입 출처를 서로 다른 속성으로 정의한다.
- 전화/카카오/문의 안내 이벤트는 채널·버튼 위치·실제 현재 페이지 종류를 일관되게 붙인다. 전역 플로팅 버튼이 블로그 위에 있어도 `page_type=global`만 남아 글별 분석에서 빠지지 않도록 한다.
- 네이티브 공유 성공 콜백을 실제 수신 완료로 간주하지 않는다. 공유 유입도 누가 공유했고 누가 받았는지의 확정 연결이 아니다.
- 홈페이지·진료·병원 소개·위치 페이지 방문은 기존 `$pageview`를 재사용한다. 모든 페이지에 새로운 사용자 정의 조회 이벤트를 중복 추가하지 않는다.

## 7. 데이터 흐름과 관리자 구성

공개 페이지 → 공통 제외·속성 검증 → PostHog → 인증된 관리자 API/HogQL 집계 → 관리자 리포트.

PostHog는 사이트 내 행동·동일 세션 흐름의 기준으로 사용하고, Search Console은 검색 노출/클릭, GA4는 기존 유입 보고와 대조용으로 유지한다. 서로 다른 도구의 식별자·기간·분모를 합쳐 전환율을 만들지 않는다. 현재 서버 인증·기간 검증·캐시·부분 실패 표시 패턴을 재사용한다. 원시 이벤트를 공개 페이지에서 조회하지 않는다.

관리자 화면은 다음 질문 순서로 구성한다. 전체 UI 교체 여부와 무관하게 적용할 수 있는 정보 구조다.

1. **운영 요약:** 측정 가능 방문, 유효 읽기, 문의 시도, 데이터 신선도/누락.
2. **유입:** 채널·첫 페이지별 방문과 이후 읽기/문의율.
3. **콘텐츠:** 글별 표본 수·읽기 단계·유효 읽기·좋아요·공유. 길이/기기/유입 필터.
4. **문의 경로:** 바로 문의 / 콘텐츠 이용 후 문의 / 병원 정보 확인 후 문의. 버튼 위치별 클릭은 별도.
5. **측정 상태:** 설정 누락·수집 시작일·버전·필수 속성 누락·중복·고아 반응·쿼리 오류.

신규 읽기 집계는 기존 전환 API에 무조건 쿼리를 추가하기보다 별도 관리자 endpoint로 분리해 해당 화면에서만 요청하는 방식을 권한다. 조회 기간 내 started-view 집합을 만든 뒤 반응을 조인하고 세션+글로 축약한다. 현재처럼 상위 N개만 잘라 전체 합계를 계산하지 않도록 전체 요약과 목록 페이지네이션을 구분한다.

## 8. 실행 단계와 완료 조건

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 1. 측정 계약 | 이벤트/속성/분모/기간/버전 정의, 기존 의미 정리 | 예시 데이터로 비율과 중복 처리가 일관됨 |
| 2. 읽기 수집 | 공개 본문 경계, 시간/깊이 추적, PostHog 전용 전송 | 자동 이벤트 상한·생명주기·제외 테스트 통과 |
| 3. 반응·문의 연결 | 목록 좋아요, 상세 view 연결, 공유 위치·전역 CTA 문맥 보완 | 실패 반응 미전송, 목록/상세 분리, 속성 누락 없음 |
| 4. 관리자 집계 | 읽기 API와 화면, 공통 기간·표본·오류·신선도 표시 | 미수집/0/오류 구별, 분모와 분자 동일 모집단 |
| 5. 운영 검증 | 승인된 배포 후 이벤트 샘플·전송량·기기별 분포 점검 | 실제 수집·집계 대조 완료, 추적 오류로 UX 영향 없음 |
| 6. 기준 조정 | 2~4주 관찰을 시작점으로 표본 확인 | 기간만 채웠다고 확정하지 않고 표본·편향 확인 후 판단 |

1차 구현은 유입 재사용 + 읽기 + 반응/문의 정합성 + 관리자 확인까지다. 추천 노출/클릭, 검색 결과 없음, 재방문은 2차다. 고객별 예약 결과 연결과 자동 노출 조정은 별도 과제다.

예상 변경 위치: `lib/posthog.ts`, `lib/blog/`의 측정 계약/계산 헬퍼, `components/blog/`의 tracker와 반응 컴포넌트, 공개 상세 페이지/렌더러의 본문 표식, `lib/admin-posthog.ts` 또는 별도 읽기 집계 모듈, 관리자 API/traffic 컴포넌트, 관련 테스트. 신규 DB 테이블·SDK 업그레이드·세션 녹화는 1차 구현에 필요하지 않다.

운영 중단은 새 읽기 추적 경계의 설정으로 가능하게 설계하고, 기존 CTA·공유 수집은 유지한다. 비활성 기간은 0반응으로 기록하지 않는다. 원격 플래그가 꺼져 있으므로 PostHog 원격 플래그에 의존하는 중단 장치를 전제로 하지 않는다.

## 9. 검증 계획

- 순수 계산: 길이·시간 경계값, 숨김/idle 시간 제외, 단계 중복, 세션/글 중복, like/unlike, 기간 경계, 분모 0, 버전 혼합, 콘텐츠 개정.
- 브라우저: 긴/짧은 글, 이미지·표·FAQ, 본문이 한 화면에 들어오는 경우, 목차/해시 점프, 빠른 하단 이동, 탭 숨김·복귀, 모바일, 화면 회전, SPA 글 전환, 뒤로가기/BFCache, StrictMode, 저장소 차단, 관리자·opt-out·SDK 미설정.
- 네트워크: PostHog payload 검증 및 GA4로 새 읽기 이벤트가 나가지 않음, view당 상한, 기존 CTA·공유 보존. 자동 테스트는 요청을 가로채거나 로컬 전송 대역을 사용해 운영 분석 데이터를 오염시키지 않는다.
- 집계 fixture: 같은 세션 반복 클릭, 목록에서만 공유, 유효 읽기 후 다른 글에서 문의, 이벤트 순서 역전, 반응만 있고 view 없는 경우, 상위 목록 밖 글 포함 전체 합계.
- UI: 키보드·포커스·목차·좋아요·공유·본문 편집·모바일 표시·reduced-motion 유지.
- 앱 코드 구현 후 `pnpm exec tsc --noEmit`, `pnpm lint`, `pnpm build` 각각 실행. 읽기용 새 Playwright spec과 기존 blog-toc/blog-faq/blog-citations, 변경한 목록·관리자 관련 spec을 실행한다. 프로젝트 규칙에 따라 기존 3000 포트 서버와 snapshot 환경을 확인한다.
- 실제 운영 검증은 코드 검증과 구분한다. 현재 health API는 전체 이벤트/CTA 존재만 확인하므로 새 읽기 수집 성공의 증거로 단독 사용하지 않는다.

이번 계획 문서에는 앱 빌드를 실행하지 않는다. 문서의 참조 경로·diff·명령을 검증한다.

## 10. 미확인 사항과 후속 확인

- 운영 이벤트 표본, 누락률, SDK 설정 적용 여부, 실제 트래픽 규모와 모바일 비율.
- PostHog 프로젝트 보관 기간·사용량·수집 호스트·읽기 API 권한. 환경변수 값은 출력하지 않고 상태만 확인한다.
- 공개 개인정보 안내는 현재 GA4 중심이다. 추가 이벤트 배포 전에 실제 수집 공급자·항목과 안내의 일치 여부를 확인한다. 이번 문서는 법적 적합성 판단이 아니다.
- 글 길이별 임계값과 표본 부족 기준은 관찰 후 보정할 가설이다. 화면 활성·스크롤로 독자의 이해도나 만족도를 확정할 수 없다.
