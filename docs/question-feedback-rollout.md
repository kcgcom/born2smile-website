# 질문 해결 피드백 전환 기록

2026-11-14 KST. 좋아요를 질문 해결 피드백으로 대체하는 시범 운영 준비다.

## 현재 상태

- 사이트 코드: 구현·검증 후 기능 브랜치에 커밋·push 완료. 이 기록 갱신 시점에는 main 병합과 운영 배포 확인 전이다.
- 운영 DB: `025_blog_question_feedback.sql` 적용 완료. 기존 좋아요 31행(누적 45회)을 삭제했고 남은 행은 0이다.
- 구 좋아요 RPC: anon/authenticated/PUBLIC 실행 권한을 회수했다. 따라서 배포 전 구 사이트의 좋아요 버튼도 더 이상 저장할 수 없다.
- 새 피드백 테이블: 생성 및 권한 확인 완료. 테스트용 응답은 롤백했고 실제 저장 행은 0이다.
- PostHog 좋아요 이벤트: 사용자 요청으로 삭제를 보류했다. 앞선 시도는 선택 삭제 API의 알파 기능 제한으로 거절됐으며, 이번 사이트 배포에서는 재시도하지 않는다. 이벤트 숨김이나 사용자 전체 삭제도 실행하지 않았다.

## 독자 경험

본문 하단에서 한 번만 ‘궁금했던 점이 해결됐나요?’를 묻고 ‘해결됐어요 / 아직 궁금해요’로 답한다. 이후 간소화 변경에서는 선택형 이유도 제거해 두 버튼과 감사 안내로 끝낸다. 자유입력은 없다. 공유 버튼은 유지하고 목록·상단의 좋아요는 제거했다.

선택형 이유 제거는 포스트 성과 패널·운영 개요 개편과 함께 배포할 변경이다. 새 UI는 저장 요청·브라우저 저장소·PostHog 이벤트에 이유를 추가하지 않는다. 기존 DB 기록을 일괄 삭제하거나 스키마를 변경하지 않으며, API의 이유 필드는 구버전 클라이언트 호환용으로 유지한다. 새 UI에서 같은 글에 다시 응답하면 기존 upsert 규칙에 따라 최종 응답이 갱신되고 이유는 null이 된다.

간소화 변경 검증: 피드백 테스트 8개와 TypeScript·lint·프로덕션 build가 통과했다. 과거 이유가 저장된 브라우저에서도 두 답변만 복원하며, 관리자 제외·저장 실패 처리를 유지한다. 이 문단은 배포 전 검증 기록이며 최종 운영 반영은 PR과 Vercel 배포 상태로 확인한다.

같은 브라우저·같은 글의 응답은 덮어써서 최종 선택 한 건을 유지한다. 이유 선택이나 답변 변경으로 응답 수가 늘어나지 않는다. 브라우저 저장소를 지우거나 다른 기기를 쓰면 같은 사람을 구분할 수 없으므로 실제 사람 수로 표현하지 않는다.

저장 실패 시 선택 상태와 성공 메시지를 확정하지 않고 실패를 표시한다. 저장이 성공한 응답만 PostHog 이벤트를 보낸다. 관리자 또는 인증 확인 중인 UI에서는 응답 버튼을 비활성화한다.

## 관리자 저장 제외

- 서버에서 관리자 이메일 허용 목록과 검증된 Supabase 토큰/세션 쿠키를 확인한다. 토큰과 쿠키가 함께 있으면 어느 쪽이든 관리자이면 저장하지 않는다.
- 세션 검증 실패·검증 서비스 장애·관리자 허용 목록 미설정은 저장 거부로 처리한다.
- 서버에서 이미 확인한 관리자 상태도 컴포넌트에 전달한다. 브라우저 관리자 표시가 없어도 관리자 세션이 있으면 API에서 차단한다.
- 로그아웃하고 관리자 표시도 없는 브라우저는 일반 방문자와 구별할 수 없다. 개인의 실제 신원을 추적하는 장치를 추가하지 않았다.
- `blog_question_feedback`에는 RLS를 켜고 anon/authenticated 직접 쓰기와 읽기를 허용하지 않는다. 저장 API의 검증을 통과한 요청만 service_role로 저장한다.

## 저장과 분석

- `POST /api/blog/feedback`: 동일 출처 JSON 요청, 제한된 크기, slug/UUID/응답/이유 검증, 발행된 글과 KST 날짜 확인. 원문 입력을 받지 않는다.
- DB에는 브라우저 생성 UUID의 SHA-256 해시를 저장한다. UUID 원문·이메일·인증 토큰을 피드백 행이나 분석 속성으로 저장하지 않는다.
- `GET /api/admin/blog-feedback`: 인증된 관리자에게 글별 해결/미해결 총계를 반환한다. 관리자 글 목록에는 해결/미해결 건수와 미해결 많은순 정렬을 제공한다.
- `blog_feedback_prompt_viewed`: 피드백 영역이 50% 이상 1초간 보일 때 기록.
- `blog_question_feedback`: 저장된 응답과 선택 이유, 응답 ID/수정 시각을 기록. GA4에는 새 이벤트를 추가하지 않는다.
- 읽기 리포트의 세션·글별 응답은 마지막 저장 시각 기준이며, 응답하지 않은 방문을 미해결로 세지 않는다. DB 전체 누적 응답과 PostHog 기간별 측정 가능한 세션 집계는 서로 다른 모집단이다.

## DB 변경 검증

운영 트랜잭션에서 전환 SQL을 먼저 실행하고 테스트 응답의 upsert·집계·권한을 확인한 뒤 전부 롤백했다. 이후 `supabase db push --linked --dry-run`으로 025만 적용 대상임을 확인하고 실제 적용했다.

적용 후 확인:

- `blog_likes` 0행
- `blog_question_feedback` 0행
- anon/authenticated의 새 테이블 INSERT 권한 false
- anon의 구 `toggle_like` 실행 권한 false

## PostHog 삭제 시도 이력 (현재 보류)

처음에는 `data_deletion:write` 권한 부족으로 403이 발생했다. 사용자가 기존 키 권한을 수정한 후에는 다음 서비스 제한으로 바뀌었다.

> This endpoint is in alpha and is not yet publicly available.

삭제 미리보기에서 거절됐으므로 삭제 요청은 제출하지 않았다. `.env.local`의 키 값은 교체하지 않았으며, 기존 키의 조회 권한은 유지된다. 후속 전체 기간 조회에서 좋아요 이벤트 17건이 남아 있음을 확인했다(앞서 최근 90일 조회의 2건과 기간이 다름). 공식 문서상 Write는 Read 권한을 포함하므로 추가로 더 넓은 권한을 부여할 문제는 아니다.

추후 삭제를 재개할 때는 선택 삭제 기능의 사용 가능 여부를 PostHog 측에 확인해야 한다. 대상은 `blog_post_like_toggled` 이벤트뿐이며, 다른 이벤트나 사용자 프로필 삭제로 범위를 넓히지 않는다. [삭제 API 문서](https://posthog.com/docs/api/data-deletion-requests), [권한 문서](https://posthog.com/docs/api/scopes).

## 로컬 검증

- 배포 브랜치 최종 검사: `pnpm test:e2e --workers=2 --retries=0` 179개 통과, TypeScript·lint·프로덕션 build 성공. 아래 개별 검사 결과는 구현 단계의 이력이다.

- 피드백·읽기·카드·관리자 관련 Playwright 26개 통과.
- 최종 관리자 표시 보완 후 피드백·관리자 테스트 15개 재검증 통과.
- TypeScript, lint, 프로덕션 build 모두 성공. 삭제된 경로의 이전 Next 생성 타입은 `next typegen`으로 갱신했다.
- 실제 PostHog 조회 코드의 변경된 피드백 집계가 configured=true, partial=false, 경고 없음으로 실행됐다. 아직 운영에 새 UI를 배포하지 않아 새 피드백 이벤트는 없다.
- PostHog 키 작업용 원격 브라우저는 사용자 로컬 화면에 보이지 않아 종료했다. 사용자 로컬 브라우저에서 기존 키 권한을 수정했다.
