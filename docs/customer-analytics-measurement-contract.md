# 고객 분석 측정 명세 v1과 구현 작업 목록

작성일: 2026-11-14. 상태: 1차 로컬 구현 완료, 운영 미배포. 검증 결과는 [구현 기록](customer-analytics-implementation.md)을 따른다.
후속 변경: 좋아요는 질문 해결 피드백으로 대체됐다. 현재 응답 정의와 삭제 상태는 [피드백 전환 기록](question-feedback-rollout.md)을 따른다. 아래 좋아요 항목은 초기 설계 이력이다.

근거: [실제 수집 점검](customer-analytics-audit-2026-11-14.md), [전체 재설계안](customer-analytics-redesign-plan.md).
‘확정’은 다음 구현의 일관된 기준을 뜻한다. 읽기 임계값이 독자의 만족도를 입증했다는 뜻은 아니다.

## 1. 1차 범위

포함: 본문 읽기 수집, 목록/상세 반응 정합성, 문의 동작 분류, 관리자 최소 리포트, 수집 품질 검사.
유지: 기존 GA4 전송, 페이지뷰/이탈 자동 이벤트, opt-out/관리자 제외, 세션 녹화 비활성화.
후속: 자동 노출 순위, 추천 노출/클릭, 검색 분석, 재방문 코호트, 예약 시스템/환자 데이터 연결.

새 읽기 이벤트는 PostHog에만 보낸다. `captureEvent`를 그대로 호출해 GA4에도 새 이벤트를 보내지 않는다. 기존 이벤트의 두 공급자 전송은 유지하되 공급자별 속성 허용 목록을 두어 새 view/session 연결 ID를 GA4에 추가 전송하지 않는다.

## 2. 분석 단위와 기간

- 운영 집계는 공식 도메인 + 공개 경로만 포함한다. local/Preview는 테스트용으로 별도 처리하며 운영 집계에서 제외한다.
- 시간은 이벤트 발생 시각, 집계 기간은 KST 전일까지 완료된 7/30/90일이다. 기존 관리자 기간 선택과의 호환을 위해 180일도 지원한다. 응답에 `periodStart`, `periodEndExclusive`, `timezone=Asia/Seoul`, `fetchedAt`, `measurementVersion`을 포함한다.
- 본문 진입마다 임의 `article_view_id`를 발급한다. 이는 영구 사용자 ID가 아니다. 해당 view의 SDK 세션 ID를 `article_session_id`로 보관해 같은 view의 연결 기준으로 사용한다.
- `article_view_id`는 같은 경로의 검색 파라미터·해시·리렌더·StrictMode effect 재실행으로 바뀌지 않는다. 다른 글로 이동하거나 새로고침하면 새 ID다. BFCache는 기존 ID/전송 상태를 복원하고 시간 기준만 재설정한다.
- SDK 세션이 회전한 뒤 활동이 재개되면 새 view를 시작한다. 이전 시간·깊이를 새 세션에 이월하지 않는다. 수집 거부 중에는 세션을 강제로 생성하지 않는다.
- 시작 이벤트와 반응은 `article_view_id + article_session_id + blog_slug + measurement_version`으로 연결한다. 중복 제거 키는 이 조합 + 이벤트 이름 + 단계다.
- 비율의 최종 단위는 세션+글이다. 같은 세션에서 같은 글을 다시 열어도 분모는 한 번이다. 읽기 조건 자체는 반드시 하나의 view에서 충족해야 한다.
- view 시작과 반응이 모두 선택 기간 안에 있어야 한다. 분모 없는 반응은 고아 이벤트로 별도 집계한다. 기간 시작 전 view의 반응을 새 방문으로 만들지 않는다.
- 세션 ID 누락, 측정 버전 누락, 비정상 범위 속성은 품질 리포트로 보내고 정상 지표에서는 제외한다. 이때 결측을 0반응으로 채우지 않는다.

## 3. 새 이벤트 계약

| 이벤트 | 발생 조건 | view당 상한 |
|---|---|---:|
| `blog_article_viewed` | 공개 본문 DOM과 메타데이터 준비 완료, 문서 visible, 수집 허용 | 1 |
| `blog_read_progress` | 깊이 25/50/75/90% 또는 활성 시간 15/30/60/90초 최초 충족 | 8 |
| `blog_read_qualified` | 같은 view의 최대 본문 깊이 ≥75% AND 활성 시간 ≥해당 글 임계값 | 1 |

합계 상한은 10이다. 재전송/중복 수신은 집계 키로 제거한다. 내부 타이머가 매초 돌아도 네트워크 이벤트는 단계 도달 시에만 보낸다. 자동 시작/단계 이벤트를 보낸 뒤에는 전송 상태를 유지해 effect 재실행으로 중복 발행하지 않는다.

### 필수 속성

| 속성 | 타입·값 | 용도 |
|---|---|---|
| `measurement_version` | `blog_read_v1` | 정의 변경 분리 |
| `article_view_id` | 무작위 문자열 | 한 번의 본문 진입 연결 |
| `article_session_id` | SDK 세션 ID | 해당 진입의 세션 연결; 외부로 노출하지 않음 |
| `blog_slug` | 정규화한 공개 slug | 글 집계 |
| `category` | 기존 카테고리 slug | 분류 |
| `page_type` | `blog_post` | 페이지 종류 |
| `page_path` | 쿼리/해시 없는 정규 경로 | 현재 위치 |
| `content_revision` | 측정 대상 블록의 결정적 해시 | 본문 개정 구분; 본문 원문 전송 없음 |
| `readable_char_count` | 0 이상의 정수 | 길이 비교 |
| `estimated_read_seconds` | 0 이상의 정수 | 실측이 아닌 추정값 |
| `required_active_seconds` | 15~90 정수, 부적격 본문은 null | 유효 읽기 임계값 |
| `reading_eligible` | boolean | 텍스트 읽기 비율 대상 여부 |

진행/충족 이벤트 추가 속성: `active_read_seconds`(0 이상), `max_body_depth_pct`(0~100), `anchor_navigation_used`(boolean).
진행 이벤트만 `milestone_type=depth|active_time`, `milestone_value`를 갖는다. 이벤트 이름에 글 제목이나 임계값을 끼워 넣지 않는다.

길이 계산은 공백을 정규화한 공개 교육 텍스트의 Unicode 문자 수로 통일한다. heading/paragraph/list/FAQ/table, 표시되는 이미지 캡션, 연구 안내의 표시 설명을 포함한다. 숨김 이미지·URL 문자열·relatedLinks·저자 소개·CTA·목차·참고문헌 목록은 제외한다. 기존 공개 콘텐츠 표시용 readTime은 변경하지 않는다.

`estimated_read_seconds = ceil(readable_char_count × 60 / 500)`.
`required_active_seconds = ceil(min(90, max(15, estimated_read_seconds × 0.25)))`.
문자가 없는 글은 `reading_eligible=false`, 임계값 null로 기록하고 유효 읽기율 분모에서 제외한다. 이미지 중심 글은 길이 비교에서 별도로 확인한다.

이 기준은 v1 가설이다. 30초 이상·60초 이상 단계와 길이별 분포를 관찰한 뒤 바꾸면 `measurement_version`도 변경한다. 과거 이벤트를 새 정의로 소급해 계산하지 않는다.

## 4. 브라우저 측정 규칙

1. 시작 이벤트는 본문이 화면에 들어와야만 발생하는 것이 아니다. 준비된 상세 페이지를 열고 본문까지 내려오지 않은 방문도 분모에 포함한다. 프리패치/숨겨진 탭만으로 시작하지 않는다.
2. 시간은 교육 본문이 viewport에 겹치고 문서가 visible인 구간만 누적한다. 현재 탭의 최근 입력 이후 60초까지만 인정한다. 최초 visible 진입을 초기 활동으로 간주한다. 입력은 스크롤·키보드·포인터 누름/이동·터치이며, 해당 내용/좌표 자체는 보내지 않는다.
3. `performance.now()` 기반으로 구간을 합산한다. 숨김·unmount·페이지 전환 때 종료하고, 5초를 넘는 비정상 타이머 간격은 누적하지 않는다. 복귀 시 이전 숨김 시간을 더하지 않는다. 정지해 읽는 독자의 과소 추정 한계는 표시한다.
4. 본문 깊이는 측정 대상 블록의 시각적 높이 합을 분모로 한다. viewport 하단의 도달 위치를 그 좌표로 변환한다. 제외 블록은 총 높이에 포함하지 않는다. 전체가 한 화면에 보이면 높은 깊이가 나올 수 있으므로 시간 조건과 함께 판단한다.
5. 목차/해시 이동을 기록하되 별도 네트워크 클릭 이벤트는 추가하지 않는다. 최대 깊이는 중간 구간을 모두 읽었다는 증거가 아니다. ‘완독’ 대신 ‘유효 읽기(추정)’로 표시한다.
6. ResizeObserver와 제한된 scroll/visibility 처리로 이미지·FAQ·화면 회전 후 크기를 갱신한다. 창 전체의 scroll depth를 본문 비율로 사용하지 않는다. 본문 개정이 바뀌면 이전 관찰 상태를 닫고 새 view로 시작한다.
7. 시작 이벤트가 SDK에 제출되기 전에 직접 반응이 발생하면 동일 문맥으로 시작 이벤트를 먼저 제출한다. 보장할 수 없는 반응은 view ID를 임의로 만들어 붙이지 않고 품질 집계에서 분리한다.
8. 수집 거부가 중간에 발생하면 읽기 상태를 폐기하고 크기 관찰을 중단한다. 재허용·세션 회전을 감지하는 경량 확인 타이머와 생명주기 리스너는 남겨두고, 컴포넌트 해제 시 모두 정리한다. 다시 허용돼도 거부 구간을 복원하지 않고 새 view를 시작한다. 저장소·SDK 실패가 본문 표시를 막지 않게 한다.
9. 마지막 종료 이벤트가 유실돼도 이미 도달한 단계는 남도록 한다. 정확한 최종 체류 시간/평균을 제공한다고 표현하지 않는다.

## 5. 기존 이벤트 보완 계약

이름은 유지하고 현재 문맥을 보완한다. 기존 역사 데이터에는 새 속성이 없으므로 시작일 이전 비율을 소급해 만들지 않는다.

| 종류 | 유지할 이벤트 | 보완 |
|---|---|---|
| 좋아요 | `blog_post_like_toggled` | `action=like|unlike`, `surface=article|list_card`, `source`, `blog_slug`; RPC 결과의 error까지 확인 후 전송 |
| 공유 | `blog_post_shared` | `method=shared|copied`, `surface`, `source`, `blog_slug`; 사용자 취소/실패는 성공 행동에서 제외 |
| 공유 유입 | `blog_share_visit` | `share_source`는 URL의 유입 출처로 유지; 공유 버튼 위치와 같은 의미로 취급하지 않음 |
| 전화 | 기존 전화 이벤트 + `footer_phone_click` | `contact_channel=phone`, 현재 페이지 종류/경로, 버튼 위치 |
| 카카오 | `contact_kakao_click`, `footer_kakao_channel_click` | `contact_channel=kakao`, 문의 완료로 간주하지 않음 |
| 문의 안내 이동 | `hero_contact_click`, `cta_contact_click`, `floating_contact_nav_click` | 연락 동작과 분리해 navigation으로 집계 |
| 지도·리뷰 | 기존 footer map/review 이벤트 | 병원 정보 확인/외부 이동으로 별도 표시 |

상세 반응에는 위 view 연결 속성을 추가한다. 목록 반응에는 상세 view ID를 붙이지 않는다. 상세 반응률의 분모는 해당 상세 페이지를 측정한 세션+글로 한정한다.

전역 Header/Footer/FloatingCTA의 위치는 `cta_location`으로 표현하고 `page_type`은 현재 페이지 종류로 정규화한다. 과거 `page_type=global`은 정규 경로로 분류 가능한 경우만 호환 집계한다. `slug`/`blog_slug`는 공통 글 식별자로 정규화하며 사용자 정의 문자열을 믿고 임의 글에 귀속하지 않는다.

공유 발생 위치를 집계할 때 `source`를 읽고, 유입 위치는 `share_source`를 읽는다. 두 값의 대응을 검증할 수 없는 행은 unknown으로 남긴다. 공유 횟수 대비 유입은 현재처럼 비율이 아닌 ‘공유 1회당 유입’이며 동일 기간의 일대일 전환이 아니다.

## 6. 관리자 지표 계약

| 지표 | 정의 |
|---|---|
| 측정 가능 본문 방문 | 시작 이벤트가 있고 reading_eligible=true인 고유 세션+글 |
| 유효 읽기율 | 위 분모 중 하나의 view에서 qualified가 발생한 세션+글 비율 |
| 깊이/시간 단계 비율 | 같은 분모 중 해당 단계에 도달한 세션+글 비율 |
| 상세 좋아요 반응률 | 상세에서 like가 발생한 세션+글 / 같은 상세 방문 세션+글; unlike는 별도 표시 |
| 상세 공유 행동률 | 상세에서 shared/copied가 발생한 세션+글 / 같은 상세 방문 세션+글 |
| 문의 동작 세션 | 전화 또는 카카오 클릭이 하나 이상 있는 고유 세션; 안내 이동 제외 |
| 콘텐츠 이용 후 문의 | 같은 세션에서 해당 글 방문 이후 문의 동작이 있었던 세션; 인과관계 아님 |

본문 반응률은 텍스트 없는 글도 별도 상세 방문 분모로 계산할 수 있지만 유효 읽기율의 eligible 분모와 섞지 않는다. 모든 리포트 응답에는 실제 분모 수를 명시한다.

표본 30세션 미만이면 ‘표본 부족’을 표시하되 데이터는 숨기지 않는다. 분모 0은 null/`—`, 수집 전은 ‘측정 전’, 비정상 연결은 ‘집계 제외’, 외부 API 실패는 오류 상태다. 30은 운영용 표시 기준이며 통계적 유의성의 경계가 아니다.

실제 PostHog 개인 API 키의 OFFSET 제한을 확인했다. 글별 목록은 slug 오름차순으로 마지막 slug를 커서에 넣어 이어받는다. 전체 요약은 목록 페이지와 무관하게 집계한다. 관리자는 수집 시작 자체가 확인되지 않았을 때 ‘측정 전 또는 수집 미확인’으로 표시해 미배포와 수집 장애를 단정하지 않는다.

기존 평균 세션 시간은 원래 의미를 표시한다. 읽기 단계 비율을 평균 읽기 시간으로 대체하지 않는다. 표본·측정 시작일·집계 기간·정의 버전·마지막 조회 시각을 함께 제공한다. 초기에는 총점과 자동 노출 순위를 만들지 않는다.

### 집계 예시

같은 글에서 A 세션은 view 2개 중 한 번 qualified, B 세션은 view 1개에서 qualified를 중복 수신, C 세션은 view 1개와 공유 복사 3회를 기록했다면:

- 본문 방문 분모는 3, 유효 읽기 분자는 2, 유효 읽기율은 2/3이다.
- 상세 공유 행동률은 1/3이고 공유 동작 횟수 3회는 별도로 표시한다.
- view 없는 D 세션의 반응은 분모/분자에 넣지 않고 고아 이벤트로 집계한다.
- 목록에서만 좋아요 한 E 세션은 상세 반응률에 포함하지 않는다.
- A가 like 후 unlike해도 ‘like 행동 발생’은 1이며 현재 좋아요 보유자 수로 표현하지 않는다.

## 7. 구현 작업 목록과 순서

| 순서 | 작업 | 주요 파일/영역 | 완료 조건 |
|---|---|---|---|
| A | 이벤트 분류·공통 문맥·전송 대상 정리 | `lib/posthog.ts`, CTA 상수/집계 | 하단 전화/카카오 포함, 안내 이동 분리, 새 읽기는 PostHog 전용 |
| B | 순수 길이·임계값·단계 계산 | `lib/blog/` 새 헬퍼 | 경계값/개정/누락 데이터 검증, 기존 readTime 보존 |
| C | 본문 측정 경계와 view 생명주기 | 공개 상세 페이지, renderer, 새 tracker/context | 정상 읽기·숨김·SPA·BFCache·StrictMode·동의 변경 검증 |
| D | 좋아요/공유 view 연결과 목록 보완 | LikeButton/BlogContent/BlogShareButton/BlogShareVisitTracker | 서버 실패 미전송, 목록·상세 분리, source 매핑 일치 |
| E | 읽기 전용 관리자 집계 API | `lib/admin-*`, `app/api/admin/posthog/` | 서버 인증·기간/버전·전체 합계·페이지네이션·부분 실패 보존 |
| F | 최소 읽기/문의/측정상태 리포트 | 관리자 traffic/insight | 분모/기간/표본/결측/정의 표시, 기존 통계 의미 수정 |
| G | 로컬 검증과 운영 검증 분리 | Playwright·계산/집계 fixture·운영 확인 절차 | 운영 분석 오염 없는 자동 테스트, 실제 수집은 별도 확인 |

A~D는 하나의 공통 계약을 따라 구현하되 작은 변경 단위로 검증한다. 첫 구현 완료는 A~G의 로컬 검증까지다. push/배포와 운영 테스트 이벤트 생성은 별도 실행 범위이며 이번 조사에서는 수행하지 않는다.

### 필수 검증 목록

- 기존 루트 규칙에 따른 TypeScript/lint/build, 관련 Playwright. snapshot이나 환경 문제로 실패하면 우회하지 않고 원인 구분.
- 시작 없는 반응, 세션 회전, 같은 글 재방문, 다른 글 전환, 잘못된 slug/버전/기간, 중복 단계, like/unlike, RPC 반환 error.
- 모바일 중심으로 본문 경계·짧은 글·목차 점프·느린 이미지·FAQ 확대·탭 전환·시간 지연 검증.
- 실제 SDK payload를 로컬에서 가로채 새 속성·호스트·공급자별 라우팅과 opt-out을 확인. mock 전송 성공만으로 운영 수집 성공을 선언하지 않음.
- 새 자동 이벤트 view당 최대 10개, 관찰자 정리, 기존 CTA/GA4 이벤트 보존.
- PostHog API와 화면의 null/0/오류/부분 응답/표본 부족 표시 검증.
- 본문 원문·입력 내용·환자/연락처 데이터 미전송. 공개 안내의 공급자·항목 일치 여부는 배포 준비 단계에서 확인.

## 8. 배포 후 확인할 기준

읽기 시작/진행/충족, 상세 좋아요/취소, 복사/네이티브 공유, 공유 링크 유입, 하단 전화 클릭을 각각 통제된 조건에서 검증한다. 분석에서 테스트를 분리할 방법과 실제 DB 반응의 영향부터 정하고 실행한다. 기존 데이터가 0건이었던 반응 경로는 자연 발생을 기다리는 것만으로 검증 완료 처리하지 않는다.

신규 지표는 수집 개시 이후부터 표시하고 운영 정의 변경은 버전으로 구분한다. 글별 표본이 충분하지 않으면 읽기율을 노출 점수로 바로 전환하지 않는다. 실제 성과 확인 전에는 전화 동작을 통화/예약으로 바꾸지 않는다.
