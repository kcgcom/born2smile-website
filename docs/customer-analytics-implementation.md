# 고객 분석 1차 구현 기록

2026-11-14. 아래는 1차 읽기 측정 구현 기록이다. 이후 질문 해결 피드백으로 좋아요를 대체했고 운영 DB의 좋아요 기록을 삭제했다. 최신 상태는 [질문 해결 피드백 전환](question-feedback-rollout.md)을 따른다. 사이트 코드는 아직 배포하지 않았다.

## 구현 내용

- [읽기 계산](../lib/blog/reading.ts)과 [추적기](../components/blog/BlogReadTracker.tsx): 본문 경계·활성 시간·깊이 단계·길이별 유효 읽기. 본문 진입 ID/세션 연결, 중복 방지, 관리자/opt-out 제외, 이미지 크기 변화·숨김·복귀 처리.
- [전송 경로](../lib/posthog.ts): 새 읽기는 PostHog 전용. 기존 이벤트의 GA4 전송에는 새 view/session 연결 속성을 추가하지 않는다. 전역 버튼의 위치와 실제 현재 페이지 종류를 구분한다.
- 좋아요·공유: 상세 반응을 읽기 view에 연결하고 목록 반응은 분리한다. 목록 좋아요 RPC의 오류 반환을 확인한 뒤 성공한 행동만 전송한다. 공유 유입은 실제 이벤트 제출 뒤 중복 표시를 저장한다.
- [문의 분류](../lib/analytics-events.ts): 하단 전화·카카오를 포함한다. 전화/카카오와 문의 안내 이동을 나누고 기존의 클릭 수 ÷ 페이지뷰 비율은 더 이상 전환율로 표시하지 않는다. 기존 API 호환 필드는 null을 반환한다.
- [읽기 집계](../lib/admin-blog-reading.ts)와 [인증 API](../app/api/admin/posthog/reading/route.ts): KST 완료 기간, 세션+글 단위 분모, 동일 view의 읽기 조건, 속성 검증/고아 view/중복 시작 점검, 부분 실패 표시, 전체 요약과 커서 목록 분리.
- [관리자 리포트](../app/admin/(dashboard)/components/traffic/BlogReadingPanel.tsx): `/admin/analysis/traffic`의 블로그 탭에 연결. GA4 오류가 있어도 독립적으로 읽기 데이터를 표시한다. 유효 읽기·30초 이상·본문 도달·좋아요·공유·문의 연관을 보여준다.
- GA4 평균 세션 시간을 ‘읽은 시간’으로 해석하던 오래/짧게 읽힌 글 순위를 제거하고, 남은 지표 이름을 평균 세션 시간으로 바로잡았다. 전체 CTA 합계 대신 운영 개요에서 전화·카카오 클릭을 표시한다.

## 운영상 의미

- ‘유효 읽기’는 75% 도달과 길이별 시간 조건을 충족한 추정이다. 이해도·만족도·완독을 보장하지 않는다. 목차 점프 여부를 속성으로 남긴다.
- 최초 읽기 이벤트가 관찰되지 않으면 ‘측정 전 또는 수집 미확인’으로 표시한다. 0% 반응으로 해석하지 않는다.
- 문의 연관은 같은 세션에서 글 이용 이후 전화/카카오 동작이 있었는지다. 여러 글에 연결될 수 있으며 통화·예약 완료나 인과 효과가 아니다.
- 목록 반응은 상세 읽기율 분모와 섞지 않는다. 좋아요는 like 행동 비율이며 이후 취소할 수 있다.
- `NEXT_PUBLIC_BLOG_READING_ENABLED=false`는 새 읽기 측정만 중단한다. 빌드 시 공개 환경변수이므로 변경 적용에 재빌드가 필요하다. 기존 CTA·공유·GA4는 유지한다.
- 모든 자동 단계 제출 후에는 크기 관찰을 중단한다. 동의/세션 변화를 확인하는 경량 주기와 리스너는 컴포넌트가 살아 있는 동안 유지한다.

## 검증

- 새 측정·집계 계약과 관리자 UI, 기존 목차/FAQ/인용/목록 복귀/필터를 포함한 관련 Playwright 41개가 통과했다. 전송 테스트는 외부 요청을 가로채고 RPC 결과를 모의 처리해 운영 분석/좋아요를 변경하지 않는다.
- SDK가 자동화 브라우저를 제외하므로 측정 테스트 안에서만 일반 방문자 환경을 모사한다. 제품의 봇 제외 설정은 변경하지 않았다.
- PostHog의 읽기 전용 API에서 요약·품질·최초 관찰 쿼리를 확인했다. 초기 OFFSET 조회는 서비스 제한으로 거절되어 커서 방식으로 변경했고 수정된 목록 쿼리는 성공했다.
- 읽기 이벤트가 아직 운영에 없으므로 실제 페이지뷰를 조회 내부에서 시작 이벤트로만 치환하는 읽기 전용 검산을 했다. 세션+글 1,785개, 글 경로 107개가 기존 독립 집계와 일치했다. 이벤트를 새로 저장한 것이 아니며 실제 유효 읽기 수집 성공을 뜻하지 않는다.
- `pnpm exec tsc --noEmit`, `pnpm lint`, `pnpm build` 모두 성공했다. 빌드는 필수 snapshot 생성을 포함했고 검사를 우회하지 않았다.
- 최종 리포트 함수의 실제 API 조회는 configured=true, partial=false, 경고 없음으로 성공했다. 새 읽기 이벤트가 아직 없어 결과는 0건이며 수집 성공의 증거로 해석하지 않는다.
- 실제 조회 중 한 차례 15초 제한에 걸렸다. 동일 SQL의 개별 순차 조회와 리포트 함수의 병렬 조회를 진단했고 이후 모두 정상 응답했다(최종 병렬 각 요청 약 0.63~0.71초). 지속적인 쿼리 결함이나 동시성 문제는 재현되지 않았고 최초 시간 초과의 원인은 확정하지 못했다. 코드에 자동 재시도는 추가하지 않았다.
- 문서 참조 경로 27개와 변경 diff의 공백 검사를 통과했다. 개발 서버는 검증 후 종료했다.

## 남은 확인

운영에 반영한 뒤 실제 모바일 브라우저의 읽기·공유·좋아요·하단 문의를 통제된 조건에서 검증해야 한다. 공개 개인정보 안내와 실제 수집 항목/공급자의 일치 여부도 배포 준비 시 확인한다. 자동 추천 점수·순위 변경, 개인별 진료 프로필, 예약 시스템 연결은 이번 범위에 포함하지 않았다.

## 관리자 좋아요 제외 보완

기존에는 관리자 브라우저의 분석 이벤트만 제외했지만, 좋아요 RPC 자체는 실행될 수 있었다. 목록과 상세 좋아요에서 공통 관리자 인증 상태가 확인 중이거나 관리자이면 버튼을 비활성화하고 저장도 차단한다. 클릭 직전에 관리자 브라우저 표시가 생긴 경우에는 [브라우저 표시 확인](../lib/admin-visitor.ts)으로 한 번 더 차단한다. 분석 수집 거부와 좋아요 기능 자체를 묶지는 않는다.

이는 사이트 UI에서 직원 반응이 섞이는 일을 방지하는 처리이며 서버 권한 제어가 아니다. 로그아웃·다른 브라우저·표시 삭제로 관리자를 식별할 수 없으면 일반 방문자와 구분할 수 없다. 기존 좋아요나 PostHog 기록은 수정하지 않았다. 앞서 조회한 90일의 2건 역시 관리자 클릭이라는 근거 없이 제외하지 않는다.
